## 1. 目标与已确认范围

基于 `kunchenguid/lavish-axi` fork，复用本地 HTML 服务、评论定位、反馈队列、agent 长轮询和回复通道，将主要交互改为 Claude Desktop 式的就地评论。

核心闭环：选择内容 → 鼠标附近打开浮窗 → 输入并提交 → 收起为圆球 → 当前 Pi session 修改 HTML 并回复 → 用户刷新查看 → 用户勾选完成 → 该评论圆球消失。

用户已明确：

- coding agent 使用的命令从 lavish 改为 `polish`。
- 在真实 Pi agent 中验证完整闭环。
- 首版支持文字选区和点击内容块，不增加任意矩形拖框。
- Polish 评论界面和新生成的 HTML artifact 使用固定的简约飞书风格；已有 HTML 保留原样。
- 浮窗不显示 `@Codex`，默认就是当前 session 的 agent。
- agent 确认接收之后到对应回复到达之前，圆球显示橙色，并同时有文字状态提示。
- 圆球内部不显示数字，通过颜色和回复标记表达状态。
- 保留 lavish 原生的选项、单选／多选、输入框和页面内表单功能，只替换侧边栏会话区；操作表单不应触发评论，选择变更本身不发送反馈。

## 3. 页面与交互

### 选择与浮窗

1. 文字选择结束或点击可评论的内容块后，显示蓝色高亮或描边，并在鼠标释放/点击位置附近打开评论浮窗。
2. 浮窗显示选区引用摘要、当前 agent 的连接状态、输入框和发送按钮。显示对象为当前 Pi session，无需手工填写 session ID。
3. 浮窗保持在视口以内：右侧或底部空间不足时自动向左/上避让。长引用截断，完整评论可滚动。
4. 页面已有按钮、链接跳转和表单操作不能被评论层无条件截获；保留清晰的评论模式入口。
5. 点击空白处或 Escape 可收起浮窗；未提交草稿保留，不能因收起而发送。

### 提交与圆球

1. 浮窗内一次提交即发送给当前 session，取消“先 Queue，再去侧栏统一 Send”的必经步骤。
2. 服务端确认接收后，浮窗收起为小圆球，锚定在对应内容块边缘。圆球跟随内容滚动，不是固定在浏览器角落的全局聊天入口。
3. 圆球支持点击重新打开该评论，展示引用、用户消息、agent 回复和继续输入框。
4. 一个未完成评论对应一个圆球；多个内容位置可以同时存在独立评论。任一时刻只展开一个浮窗。
5. 发送失败保留输入并提供重试；未收到确认时不能表现为成功收起。重试或刷新不产生重复评论。

### 刷新与用户验收

1. 按用户原始表述，首版以手动刷新查看新版 HTML 和回复为基准。后台可以更新连接/处理状态，但不因 agent 保存文件而强制打断阅读。
2. 点击页面刷新入口或浏览器刷新后，恢复未完成评论、圆球、回复和可恢复的阅读位置。
3. agent 的回复只表示“已回复，待确认”，不能自动完成评论。
4. 用户打开圆球查看结果；不满意可在同一评论继续提交，进入下一轮处理。
5. 用户勾选“完成”后，持久化完成状态，关闭浮窗并移除该圆球与临时选区高亮。再次刷新也不能复活该圆球。
6. 完成针对当前评论，不结束 Pi session，也不完成其他评论。历史保留，首版无需新增历史管理界面。
7. HTML 修改导致原定位失效时，保留评论并明确显示“原内容位置已变化”，提供可访问入口；不能把评论悄悄挂到其他相似段落，也不能丢弃评论。

### 评论状态

| 状态     | 显示                                    | 进入条件                     |
| -------- | --------------------------------------- | ---------------------------- |
| 草稿     | 浮窗输入框                              | 用户开始输入                 |
| 发送中   | 发送进度                                | 请求已发出，尚未收到接收确认 |
| 等待处理 | 收起圆球，可重新打开                    | 服务端已接收，agent 尚未取走 |
| 处理中   | 橙色圆球及“agent 已收到 · 正在处理”提示 | 当前 agent 已取走该反馈      |
| 待确认   | 有回复标记，圆球仍保留                  | agent 回传对应评论的回复     |
| 已完成   | 圆球消失                                | 用户主动勾选完成             |

连接状态与评论状态分开。没有监听中的 agent 时如实显示等待连接，不伪装为正在处理。

## 4. 固定视觉风格

- 白色内容面、浅灰页面底色、深灰正文、蓝色主要操作和选区描边。
- 系统无衬线字体，清楚的字号层级，适度留白、细边框、小圆角和轻阴影。
- 评论浮窗与圆球统一使用这套样式，不提供主题选择器。
- 新生成的 HTML 通过固定模板/样式指导写入文件，直接打开时保持相同外观。
- 已有 HTML 不被评论工具自动重新设计；评论覆盖层使用 Polish 样式即可。
- 默认以 artifact 为页面主体，评论主要在就地浮窗完成，不常驻宽聊天侧栏。

## 5. 命令与 Pi session

Pi 版本实际命令接口（详见正式开发书 v1.3）：

```sh
polish artifact.html
polish status artifact.html
polish design
polish end artifact.html
```

- `polish` 是实际可执行命令，不只是将网页标题改名；help、错误提示、下一步提示和 agent skill 中的调用示例必须同步。
- 若通过 skill 调用，入口命名为 `polish`（例如支持 slash skill 的客户端中的 `/polish`）。npm 发布不是本轮验证的前提，可先使用本地构建链接。
- 当前 session 指加载 Polish 扩展的那个 Pi 对话。扩展在该进程内自动投递与关联回复，不另起模型对话；不需要手动 poll/reply。
- HTML 的规范化绝对路径继续标识 artifact 会话；一个 artifact 同时只有一个反馈监听者，不能静默接管另一个监听者。
- 每条评论和对应回复需要稳定关联。现有 session 级批量回复不能直接广播为所有圆球的回复；实现时需让 agent 取得评论标识并支持按评论回复。
- 回复完成不等于用户验收；`end` 只在结束整个评审会话时使用，不与单条评论的“完成”混用。
- Pi 空闲等待、处理途中收到后续评论、重新进入轮询后接收反馈，均需要实际验证，不能以 HTTP 模拟替代。

## 7. 实施顺序与验收

1. 命令与通信 → 验证 `polish --help`、open/status/end 及自动回复关联可用，反馈与回复能准确归属评论，用户完成可持久化。
2. 就地评论交互与固定样式 → 浏览器验证选区、浮窗避让、提交收球、展开追问、刷新恢复及完成消失。
3. Pi 真实闭环 → 由同一个 Pi session 执行工具并修改测试 HTML，保存会话记录和浏览器证据。

必须通过的端到端用例：

- Pi 打开已有 HTML；用户选中一段文字，提交“将标题改为指定文字”；Pi 收到正确引用和定位，修改实际文件并回复；用户刷新看到新标题和回复；勾选后圆球消失。
- 对一个内容块提交修改；在同一评论追加一次要求；两轮都由同一个 Pi session 接收并回复。
- 同时存在两条评论时，回复和完成各自独立，完成 A 不会让 B 消失。
- agent 已回复但用户尚未勾选时，刷新后圆球仍存在；完成后刷新不再出现。
- agent 未监听、发送失败和重试时，状态真实且输入不丢失、不重复发送。
- HTML 改动使锚点失效时，评论仍可访问且不误定位。
- 已有 HTML 的原样式保持；新生成的测试 HTML 使用简约飞书模板。
- 运行仓库规定的 `pnpm run check`，并完成覆盖本次改动的浏览器验证。
