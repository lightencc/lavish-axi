只推进 Pi；Codex 后置且未通过。此目录的代码是机制验证，不是 M1–M3 产品实现。

1. 保存 v1.1 及两轮证据，更新阶段范围 → 核对旧 manifest；核心门槛不变。
2. 先写故障／身份测试，再做最小持久 inbox 与查询 → 验证同键同载荷、异载荷冲突、跨实例拒绝、未决不重投、权威历史正向核验；空结果不能作为未收依据。
3. 在专用 Pi RPC 进程显式加载扩展，记录 ready 的 PID／随机实例 ID／session ID；之后才建立桥接绑定 → 同一进程内验证宿主持久接纳、消费输入、持久回复关联、重复查询。直接调用只算组件证据。
4. 准备最小网页桥接：固定会话，不接受客户端 session／命令／路径；Host／Origin 校验；不使用正文猜回复，不新增依赖 → 无监听的接口测试。
5. 网页端到端 → 当前禁止新增监听，停在启动步骤。计划仅 `127.0.0.1:49793`，仅此隔离页／submit／query，临时进程，连接第 3 步已运行实例，无持久凭据。现有 49791／49792 属于原型，不接管、不改绑。获准后才能验证真实浏览器，不能用组件测试冒充。
6. 报告 G01–G07 和故障窗口 → Pi 未通过的门槛保持 BLOCKED／FAIL／NOT RUN；停止于 M0 供独立审证。

最小方案：网页提交先进入桥接持久记录，再通过已持有的 RPC 通道调用公开扩展命令。宿主扩展持久 inbox 成功才发业务接纳回执；RPC handled 不算。空闲时处理 inbox，忙碌时留在扩展持久队列；进入 Pi 模型请求上下文后记录真实输入证据，turn_end 后记录宿主条目 ID。查询核对固定实例／session、消息 ID、摘要和宿主分支条目。公开 API 调用与持久记录之间的不可判定窗口仍停未知，禁止自动重投。

宿主扩展队列不是 Pi 原生 followUp 队列的持久性保证。任何局部成功都必须注明边界。结束排空／无漏重连和 30 次网页性能样本要在完整链路可运行后独立验证；不先建模拟器来宣称通过。
