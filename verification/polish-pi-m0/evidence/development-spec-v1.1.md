# Polish 正式开发书

版本：1.1 · 日期：2026-10-30（Asia/Shanghai）· 状态：文档修订，待独立复审；未获完整开发放行。

本次仅修订开发书，不开展 M0 实验或 M1–M3 实现。M0 是受控可行性验证，文档列出验证方法不代表授权执行；M0 通过也不自动授权完整开发。版本变更对照见第 12 节。

本文汇总用户的录屏参考、原型体验及后续修订意见，作为正式研发与验收依据。原型中已有的行为不自动等于正式产品契约；发生冲突时以本文和用户后续指示为准。

## 1. 产品目标

基于 lavish-axi fork，保留其 HTML artifact 展示、页面内交互和 agent 通信基础，将常驻侧边栏会话区替换为就地评论浮窗和状态圆球。用户直接指出修改位置，与当前 session 的 agent 交流，刷新检查结果，再确认完成。

**响应效率为 P0。** 网页发送必须主动投递到绑定的 agent 会话，并在该会话空闲时触发处理；不能依赖用户回到聊天窗口提醒，也不能依赖模型偶尔想起执行 poll。

正式版必须在真实 Pi agent 中完成端到端验收；当前原型使用当前 Codex 会话确认产品交互。

## 3. 两种消息必须分开

### 3.1 定位评论

来源是用户主动选中文字或点击内容块。包含真实的选区引用、可恢复的定位信息、评论 ID 和修订轮次。

提交后在对应内容旁显示圆球。回复、追问、待确认和完成均归属于这一条评论。每条未完成评论对应一个圆球，一次只展开一个浮窗。

文字定位需要引用及范围信息；DOM selector 只标识容器，不能单独代表文字选区。修改后不能可靠恢复位置时，保留评论并显示“原内容位置已变化”，转入可访问的未定位评论入口，不能误挂到相似段落。

### 3.2 整体提交

整页确认、全局修改意见和不针对某个元素的表单提交属于 artifact 会话级消息：

- 不要求 selector、DOM 节点、选区文字或坐标；不把 `body`、某张卡片或表单容器作为虚构锚点。
- 不显示选区引用，不高亮网页内容，不在内容块旁产生圆球。
- 保留消息 ID、提交内容、所属 artifact 会话及回复关联，仍然可以追问。
- 顶栏设置轻量的“整体意见”入口，展开会话浮窗，承载全局输入、历史、状态及回复，替代原侧栏的全局会话功能。
- 页面内的整体提交可直接发送并在提交处给出回执；查看后续回复使用“整体意见”入口，无需先进入定位评论浮窗。
- 带真实语义定位的原生控件仍可提供其上下文；表单问题 ID 和答案是业务数据，不等于需要画圆球的元素锚点。

原型把“确认这版功能”挂到 `scope-behavior`、把整体表单挂到表单元素的做法不进入正式版。

## 4. 交互与视觉契约

### 4.1 选择与输入

1. 评审页默认启用评论交互，文字选择结束或点击内容块，立即显示浮窗，无需先切换模式；支持标题、普通正文、跨段文字以及鼠标移出选区后释放。
2. 浮窗以鼠标释放／点击位置为起点，自动向左或向上避让，输入和发送操作保持在可见视口内。
3. 显示必要的引用和会话状态，不显示 `@Codex`，不要求输入 session ID。
4. 点击空白或 Escape 收起；未提交草稿保留，不自动发送。支持键盘进入评论及快捷键发送。
5. 表单、输入框、按钮、链接、可编辑区域和已有交互组件按原逻辑工作，评论事件不能劫持它们。

### 4.2 发送、圆球与状态

| 状态 | 触发依据 | 定位评论表现 | 整体提交表现 |
| --- | --- | --- | --- |
| 草稿 | 尚未提交 | 浮窗／可恢复草稿标记 | 会话输入或表单中保留 |
| 发送中 | 正在等待服务端接收回执 | 可见发送反馈，防止重复提交 | 提交控件显示发送状态 |
| 等待接收 | 已持久化，agent 尚未确认消费 | 蓝色无数字圆球，提示等待接收 | 全局入口显示等待接收 |
| 处理中 | 对应消息已进入 agent 当前处理输入 | 橙色无数字圆球，提示 agent 已收到 | 全局入口显示橙色处理提示 |
| 已回复／待确认 | 对应轮次的回复已保存 | 恢复蓝色，出现新回复标记 | 全局入口显示新回复提示 |
| 已完成 | 用户明确勾选该评论完成 | 圆球和临时高亮消失 | 会话级确认记录，不伪造评论圆球 |
| 结果未知 | 请求可能已到达宿主，但缺少可核实回执 | 提示“正在核实接收结果”，不伪装处理中、不提供盲目重发 | 全局入口显示同一核实状态 |
| 失败／需处理 | 投递或执行得到明确失败结果 | 保留评论、输入和可操作错误提示 | 全局入口给出原因及重试方式 |

收到 HTTP 成功、进入宿主消息队列、agent 实际接收是不同事件。只有实际接收回执可触发橙色。已有任务占用 agent 时及时显示“agent 正忙，已排队”，不能把排队冒充正在执行。

同一评论追加要求后进入新轮次；旧轮次的迟到回复不能结束新轮次的橙色状态。只更新对应评论，不能用某条回复把所有已投递评论都标成完成。

### 4.3 刷新与完成

- 连接状态、接收回执、圆球颜色和新回复提醒实时更新，不要求先刷新。
- HTML 及回复正文默认由用户手动刷新检查，保留原确认流程；agent 保存文件不能强制打断阅读和输入。
- 预期行为是实时告知“有结果”，用户决定何时载入结果；不得借此延迟 agent 的实际投递与执行。
- 刷新恢复滚动位置、草稿、表单答案、未完成评论、定位和状态；只恢复本工具负责的状态，不覆盖页面自身业务状态。
- agent 回复只进入待确认。完成请求携带用户实际加载并查看的 `review_epoch`、`comment_id`、`round_id`、回复版本及 `artifact_revision`；服务端在同一存储锁内核对当前代次、最新轮次及修订。任何不匹配均拒绝完成并提示刷新，不得把客户端未查看的内容标为已验收。
- 完成与新追问串行提交：追问先提交则旧完成请求冲突；完成先提交则随后有效追问创建新轮次、恢复未完成状态。完成请求重试幂等，刷新不复活已经完成且没有后续追问的圆球。整页确认同样核对已查看的会话版本和 artifact 修订；不能遗漏并发新增意见。
- 单条完成不关闭整页，不结束整个 artifact 通信，也不终止 coding agent 会话。

### 4.4 样式

固定白色内容面、浅灰背景、深灰正文、蓝色主操作及橙色处理中状态。使用系统无衬线字体、清晰层级、细边框、适度圆角和轻阴影。状态同时提供文字或无障碍标签，不能只靠颜色。

新 HTML 通过模板／设计指导把样式写进文件，离开 Polish 直接打开也一致。已有 HTML 的样式不被服务端重写，评论层保持自身样式隔离。

## 5. 保留原生页面交互

侧栏是被替换的展示和输入区域，原有 artifact SDK 与交互协议继续工作：

- 单选、多选、文本框、选择器和自定义交互仍正常响应；选项变化只更新本地状态。
- 显式提交才产生反馈；保留既有 `queuePrompt`、队列替换／合并及立即发送能力，不强制重写已有 artifact。
- 原生“先排队后统一发送”的页面继续受支持：将待发送状态和提交入口迁入紧凑的全局会话入口，不因为侧栏消失而丢失队列。
- 定位评论的发送按钮采用一步提交，不把用户送回全局区再点一次发送。
- 保留原生表单的结构化答案及 `question`／`queueKey` 等语义。整体表单反馈默认无锚点；显式定位反馈沿用其真实上下文。
- 本产品新生成的 SDK 命名可使用 `window.polish`；已有 `window.lavish`、`data-lavish-*` 标记及语义保留兼容。命令改名不等于要求用户重写旧 HTML。

## 6. 会话结束与关闭网页

这里的“结束通信”指停止该 HTML 评审的投递、监听和自动唤醒，不是退出 Pi/Codex 程序、终止其他会话或删除历史。

### 6.1 三个动作

| 用户动作 | 契约 |
| --- | --- |
| 单条评论勾选完成 | 只结束该评论，其他评论与全局通信继续 |
| 整页确认后关闭／确认并结束 | 整体确认作为无锚点消息提交；服务端确认记录并结束该 artifact 通信后关闭评审页 |
| 手动“结束通信” | 随时可从顶栏菜单发起，持久化用户结束原因，进入 ending 排空；达到 §6.2 的消费门槛后才停止监听和后续唤醒 |

### 6.2 结束排空契约

生命周期为 `open → ending → ended`，进入 `ending` 就关闭新消息入口，只有排空成功才显示“通信已结束”。`ending` 是持久化状态，不是前端倒计时。

| 动作／阶段 | 必须原子保存或核对的事实 | 允许的后续行为 |
| --- | --- | --- |
| 发送并结束／确认并结束 | 在 `store.lock` 内保存稳定 `end_request_id`、当前评审代次、最终消息及结束标记、所有此前已接受消息构成的固定排空集合，并切到 `ending` | 只交付此集合；并发提交若先获得锁则纳入集合，若后获得锁则拒绝且保留客户端输入 |
| 保留未发送内容并结束 | 持久化结束请求、结束标记与已接受消息集合并进入 `ending`；草稿及仅在浏览器排队的内容留在原客户端，不加入投递集合，不伪装为已提交 | 已被服务端接受的消息仍需排空；未提交草稿在显式 reopen 后可恢复，但不自动发送 |
| `ending` | 对每条待交付消息保存第 7.5 节的投递状态，结束标记同样具有稳定身份 | 排空任务可在没有浏览器连接时继续；只允许集合内的安全投递、核实、回执及关联回复，不允许追加新的用户消息 |
| `ended` | 集合内全部消息及最终结束标记已取得当前绑定宿主的真实消费回执，回执已持久化 | 停止投递与唤醒，释放该 artifact 的监听；历史及迟到回复可归档，不再驱动评审状态 |

真实消费回执必须能证明消息已进入绑定 session 的处理输入（见第 7.5 节），本地保存、写出 poll 响应、HTTP 成功或宿主排队回执均不足以进入 `ended`。宿主忙碌时保持 `ending` 并显示“等待 agent 接收最后反馈”；不打断其当前任务。结束标记应随最终集合或在此前消息全部交付后有序消费，不能先结束宿主侧评审再交付反馈。无需等待模型回答或文件修改完成。

结束请求和重复提交在查重时先验证身份、代次与原始载荷：同一请求返回已存状态，内容不同则冲突；`ending`／`ended` 下不得借重试 ID 创建新消息。终止集合封存后不可扩展。所有排空行为仍由第 7.5 节的唯一消费者负责。

- 保存后、投递前崩溃：重启读取同一个排空集合和投递账本，继续未开始的安全投递，不再创建结束请求。
- 调用宿主后崩溃、超时或丢回执：标记结果未知，按第 7.5 节查证，不能当成失败自动重发，不能进入 `ended`。
- 明确未接收的失败：保留 `ending` 和消息，给出原因；只有符合安全重试条件才重试原身份。持续失败或无法核实则显示待处理限制，不能宣称结束成功。
- `ending` 期间关页不取消排空，也不自动重开浏览器；服务不可用时重启后恢复，不能承诺进程未运行期间仍可交付。保留未发送草稿仅保证原客户端存储范围。

用户主动结束的入口同时包含“发送并结束”“保留未发送内容并结束”“取消”；“取消”仅在结束请求提交前取消操作，已封存的排空集合不能通过 UI 取消而悄悄丢弃。最终回执前显示“正在结束”，不能自动关闭并显示成功。用户仍可自行关页，后续重新查看时如实展示 `ending` 或 `ended`。

浏览器不允许脚本关闭用户手动打开的标签时，显示“通信已结束，可关闭此页”；通信结束不依赖 `window.close()` 成功。结束前已被接收的修改仍可能继续执行，不能标为取消；不终止宿主进程或其其他任务。

### 6.3 关闭和断线的默认解释

以下是为消除实现歧义规定的研发默认值，不是现有原型已实现的能力：

1. 整页已经明确确认、且没有待发送或待处理事项时，关闭最后一个评审标签触发上述结束流程；采用现有约 10 秒重连宽限，避免把刷新误判为结束。确认本身的消费回执也必须满足排空条件，不能直接跳到 `ended`。
2. 未整页确认时意外关页、刷新、崩溃或网络断开，按断连处理并保留状态，不标为用户已验收。宽限后停止无意义的等待；不自动重开浏览器。
3. 多标签情况下，关闭其中一个不会结束仍被其他标签使用的评审。
4. `beforeunload`／关闭信号只能辅助提示；终止状态由服务端持久化和最后连接状态确认，不能只依赖一个可能丢失的浏览器请求。
5. `ending` 拒收新评论但继续受控排空；`ended` 禁止新投递、自动唤醒和定时重开。只有 `ended` 且用户明确重新评审才使用 reopen，建立新的 `review_epoch`；`ending` 不允许 reopen 绕过未完成投递。
6. 结束前已被 agent 接收的修改不会被伪装成已取消。反馈中标明用户已请求结束评审，余下工作如需完成可在原 agent 会话交代；不重新打开网页，也不误杀当前会话其他任务。

## 7. P0：响应效率与当前 session 绑定

### 7.1 必须解决的原型缺口

原型能通过 CLI 队列在当前会话收发，但后台 `poll` 完成不保证在 Codex 回合结束后自动唤醒模型；浏览器还每 4 秒获取状态。因此“真实收发已验证”不能推导为“会话即时唤醒已实现”。这两项缺口必须在 P0 解决。

### 7.2 目标路径

网页提交 → 本地服务持久化与去重 → 立即调用绑定宿主的会话投递接口 → 宿主接收／启动处理 → 回执实时推送至页面 → agent 修改文件并回传带关联的回复 → 页面实时提示结果。

- 同一 artifact 绑定同一个宿主 session，绑定信息在创建时取得并保存。网页不能提交任意目标 session 来改变路由。
- 宿主空闲时主动启动其下一处理回合；宿主正在工作时使用其受支持的消息队列，自动在可处理时消费。不得默认中断用户正在执行的任务。
- 不另外启动模型会话来冒充当前 session。仅 `resume` 一份历史、启动另一个进程，不足以证明已绑定当前活动会话。
- 本地接收与宿主执行是两个确认边界；明确未接收才可按策略重试，超时及丢回执进入结果未知，按第 7.5 节处理。
- 服务端复用 WebSocket 推送接收、回复、连接和结束事件，取消固定 4 秒状态轮询。按第 7.6 节先订阅并缓存，再合并带版本的快照，避免重连漏事件。
- 同一消息只允许一条消费路径。主动投递与遗留 poll 共享第 7.5 节的唯一消费权，不能独立破坏性取走同一批消息。

### 7.3 宿主接入顺序与证据

**Codex：** 本机 CLI 已通过 `codex queue --help` 确认存在 `codex queue --thread <THREAD> --message <TEXT>`，用于向既有 session 排队。优先验证该入口是否实际连接当前桌面会话、是否可在空闲时启动处理、忙碌时如何排队、失败与重复投递如何返回；目前尚未实测这些语义，不能写成已通过。

官方 App Server 文档说明 `turn/start` 可启动目标 thread 的回合，`turn/steer` 可向活动回合追加输入，后者要求正确的 `expectedTurnId`。这些是候选宿主能力；能否访问当前桌面持有的同一个服务实例仍须本机验证，不能仅凭 API 名称推断已接通。[官方文档](https://learn.chatgpt.com/docs/app-server)

**Pi：** 本机已确认 Pi 1.4.0 提供扩展与 RPC 模式。P0 读取该安装版本的扩展／消息接口，选取向当前运行中 Pi session 发送用户消息的最小接入点。仅通过另起一个 `pi -p` 进程响应不算验收成功。要验证空闲、忙碌、回合结束、恢复连接四种情况。

保留一个小型宿主桥接边界即可；不建设通用插件框架。桥接只负责确定会话、投递、接收回执和释放评审监听，继续由既有 agent 负责推理与文件修改。

### 7.4 性能目标及测量

以下为建议的首版工程验收门槛，尚非实测成绩。条件：本机服务、宿主已启动、模型与网络条件记录完整；宿主空闲场景单独统计。

| 指标 | 起止点 | P95 目标 |
| --- | --- | --- |
| 选择反馈 | 选择结束 → 浮窗可见 | ≤ 100 ms |
| 发送反馈 | 点击发送 → 按钮显示发送中 | ≤ 100 ms |
| 持久化回执 | 点击发送 → 本地服务确认接收 | ≤ 500 ms |
| 宿主投递 | 服务端接收 → 既有宿主会话接受投递 | ≤ 1,000 ms |
| 接收状态展示 | agent 接收事件 → 浏览器橙色状态 | ≤ 200 ms |
| 回复通知 | 回复已落库 → 浏览器出现新回复提示 | ≤ 200 ms |

每个阶段记录关联 ID 与时间戳，避免混用未经校准的浏览器和服务端时钟。至少采样 30 次简单往返，记录 P50、P95、最大值、错误率和未完成样本；不能剔除失败请求美化结果。

“宿主接受投递”与“模型开始处理”分别计时。模型首 token、工具执行、排队和完整回答时间另列；不承诺任何复杂修改都在一秒完成。增加同模型、相近上下文的直接聊天对照，定位 Polish 额外开销。忙碌时及时确认排队，不把排队时间计成空闲宿主投递延迟。

**门槛：** 没有实现 idle 状态自动唤醒，或仍需用户在聊天框催促，P0 直接不通过；即使 UI 已变快也不能进入正式交付。

### 7.5 投递账本、结果未知与唯一消费权

本地 message ID 只能防止重复入库，不能证明宿主只执行一次。服务端必须为 `(artifact key, review_epoch, message_id)` 持久化投递账本，并绑定宿主实例／session 身份、载荷摘要、稳定宿主幂等键（若支持）、尝试记录和宿主消息／回合回执。调用宿主前先落盘 `dispatching`；重试保持原身份和原载荷，不生成新的幂等键。

| 投递事实 | 可接受的证据 | 恢复／重试规则 |
| --- | --- | --- |
| `accepted` | 本地服务持久化成功，尚未开始宿主调用 | 可由唯一消费者首次投递 |
| `dispatching` | 已持久化即将调用宿主，外部结果未落盘 | 崩溃后按结果未知核实，不能假设请求没发出 |
| `host_queued` | 宿主返回可关联消息的排队回执 | 不重复投递；等待该身份被消费，不触发橙色 |
| `delivered` | 宿主事件或可核实记录，证明确切消息已进入绑定 session 的处理输入 | 持久化消费回执，才触发橙色；执行失败另行报告，不因此重发用户消息 |
| `delivery_unknown` | 超时、连接中断、丢回执或重启发现未决调用 | 暂停该消息重投并查询原身份；显示“结果未知，待核实”，既不是失败也不是已处理 |
| `not_accepted` | 宿主明确拒收，或权威查询确认原调用已终止且未接收 | 按原因允许原身份重试；鉴权／能力不支持等持续错误先解决，不循环轰炸 |

核实优先查宿主消息／幂等键回执。查到排队或消费事实就推进账本；暂时查不到、最终一致查询的空结果不等于未接收。宿主若支持有持久去重保证的幂等键，可在其保证范围和有效期内重试同键；有效期到期或语义未经验证时不能重投。回执必须校验宿主身份、评审代次、消息及载荷，不能按相似正文或“当前有一个回合”猜测。

若宿主既不能提供可验证的幂等保证，也无法查证未决投递，则保留 `delivery_unknown` 并停止自动重投，提供原消息身份、时间和核实说明。人工核实必须留下绑定宿主的可关联证据；没有证据不能提供宣称安全的“一键重试”或“已送达”。这是明确的可恢复性限制，相关 M0 恢复门槛不通过，不能宣称 exactly-once；本地账本并不能消除外部调用的不确定性。

主动桥接和遗留 poll 通过同一权属协调器领取消息，在 `store.lock` 下持久化消费者模式、批次和 claim 代次；网络调用不持有存储锁。沿用 `activePolls`／`pollOwnershipLock` 的互斥原则，扩展到桥接路径。切换消费模式必须显式且先结清未决交付；后来的消费者不得拿走已 `dispatching`／`host_queued`／未知的消息。重启先恢复账本，再开放消费；lease 超时或旧消费者离线本身不证明宿主未接收。旧 claim 不得提交新状态或继续发起新调用；已在途调用仍按未知结果查证，不能靠换 claim 当作外部调用已被取消。

遗留 poll 写出响应仅能证明传输尝试，正式版需由当前宿主桥接确认具体消息被消费；保留上游断开恢复能力，但恢复后的批次必须经过同一账本核实，禁止绕开未决状态盲目重投。原有批量 `delivered_at` 不直接替代正式消费证据。

### 7.6 无漏事件的重连同步

沿用 [invariants 的 Request flow](invariants.md#request-flow) 中“先注册通道，再读结束状态”原则，选定以下协议，不使用先拉状态再订阅：

1. 服务端先注册当前 artifact 的事件通道并缓存事件，再在存储锁内取得完整快照及持久化单调 `state_version = V`。状态变更和版本递增在同一事务内；每个版本对应一条可合并事件（批量变更使用一条批量事件），不得因过滤事件制造无解释的缺号。快照含 `review_epoch`、投递／评论／生命周期事实。版本跨进程重启持续递增，不因 reopen 归零。
2. 客户端在同一同步连接接收快照，期间缓存实时事件。先应用版本 V 快照，再按版本处理大于 V 的连续事件；小于等于 V 的重复事件丢弃。快照后的事件先到达客户端也先缓存，不得被旧快照覆盖。
3. 每次同步有连接／同步代次标识；旧连接的快照或事件不得覆盖新同步状态。同一连接不接受倒退快照；短暂乱序先缓存，缺号、缓存溢出、历史缺口或服务重启造成续接失败时重新执行“先注册通道再取快照”，不猜测丢失状态。无需首版建设无限事件历史。
4. 处于同步或缺口期间保留当前已知状态并提示重连；完成、结束等写入仍由服务端按版本校验，不把 UI 过时当作写入授权。回复和结束事件不能因为用户未刷新正文而被忽略；自动同步仅更新状态与结果提醒，正文加载仍遵守第 4.3 节。
5. epoch 改变必须由新快照确认后切换；旧代次的回复可归档，但不会生成当前代次事件或改变圆球／结束状态。服务重启若不能恢复版本连续性，强制全量重新同步，不能复用可能倒退的游标。

### 7.7 M0 的受控验证门槛

M0 只验证接入可行性及故障契约，不等于完整产品交付或 M1–M3 放行。Codex 与 Pi 必须分别填写下表并提交证据，不能用一方结果代替另一方，也不能只验证正常路径。

| 门槛 | 每个宿主必须提交的证据 |
| --- | --- |
| G01 同一活动 session | 宿主实例与 session ID、网页绑定记录、发送前后同一对话记录；另起进程重放历史不算通过 |
| G02 自动处理 | 空闲及上一轮结束后均自动唤醒；忙碌时排队，默认不打断当前任务 |
| G03 三级回执 | 本地持久化、宿主排队、真实消费各自的消息 ID、时间和事件依据；不使用 HTTP 成功冒充消费 |
| G04 外部不确定性 | 注入丢回执和超时，证明可查证或受宿主幂等保护；无保证时安全停留未知并列为未通过恢复门槛 |
| G05 恢复与唯一消费 | 掉线、桥接／服务重启、重复请求、主动桥接与 poll 并发时的账本与宿主执行记录，证明无盲目重复执行 |
| G06 结束与同步 | 第 6.2、7.6 节交界故障测试，证明最终消息不滞留、不会提前 ended、回复和结束事件不丢失 |
| G07 延迟与失败 | 分别报告持久化、宿主排队、真实消费、模型开始、首 token、回复通知，保留失败、未知和未完成样本；按第 7.4 节采样 |

任何未通过或未提供证据的项都阻止进入 M1–M3。验证不得修改平台权限、绕过沙箱／审批或生成持久凭据；如当前宿主能力不足，记录具体限制并提交复审，不静默扩大权限或换一个会话。

### 7.8 安全与信任边界

正式实现复用 [AGENTS.md](../AGENTS.md) 与 [invariants](invariants.md) 的既有边界，尤其是 Process model、Request flow 和 Things to know when editing；原型不能作为放宽边界的理由。

- artifact iframe 保持无 `allow-same-origin` 的沙箱及对应 artifact 响应 CSP；评论正文和会话状态由可信 chrome／服务端管理，不为了浮窗把宿主接口暴露给 artifact。
- artifact→chrome 消息必须走 `postArtifactMessage`，核对当前 frame 的 `event.source`、当前 `artifact_load_token`、载荷类型及大小；令牌不是持有即授权，也不能替代来源核验。旧页面令牌不可操作新加载实例。
- 保留 Host allowlist、Origin／Referer 验证、规范路径与 symlink 隔离；完成、结束、reopen 和桥接控制同样受对应边界约束。保留受信本机 CLI 无 Origin 的既有控制路径，不扩为浏览器任意来源访问。
- 绑定宿主实例、session、允许的调用方法只由可信服务端／宿主集成确定。网页及 artifact 传来的任意 session、命令或路径不能改变绑定，评论文本只作为数据传递，不能拼接成 shell 命令。artifact key 不是授权凭据，不能凭 key 越权结束另一评审。
- 用户评论、引用、表单值及错误文本一律安全转义；agent 富文本仅经受控渲染路径，危险标签、事件属性及 URL 不执行。恶意内容不能借浮窗跨入 chrome 权限。
- 桥接遵守当前宿主沙箱和审批策略，不扩大权限，不在 HTML／浏览器存储中放置宿主凭据，也不为验证生成持久凭据。

## 8. 数据和命令约定

### 8.1 身份与关联

| 标识 | 作用 |
| --- | --- |
| artifact key | 沿用 HTML 规范化绝对路径身份，不作为访问凭证 |
| agent session ID | 宿主对话身份，与 artifact key 分开保存 |
| review_epoch | 每次显式 reopen 新建的评审代次，隔离旧请求、回执及回复 |
| state_version | 跨重启持久单调状态版本，用于快照／事件合并 |
| end_request_id | 固定结束请求及排空集合身份，不随重试变化 |
| comment ID | 定位评论的持续讨论身份；整体消息不强制具有 comment ID |
| message ID | 单次提交／回复的稳定身份，用于幂等与确认 |
| round ID / reply-to | 将回复绑定到确切提交，处理追加要求和迟到回复 |

消息以 `scope: anchored | session` 区分。`anchored` 必须包含有效的定位与引用上下文；`session` 不包含虚构 selector。结构化表单答案作为消息数据保存。

本地 accepted、host_queued、delivered、delivery_unknown、replied、resolved 及明确失败等事实按第 7.5 节分别记录。正式版不把状态协议藏在 `[polish:…]` 文本前缀里，不通过匹配用户正文判断回复归属。完成状态保存在会话存储；浏览器 localStorage 可用于未发送草稿，不能作为已发送评论完成状态的唯一来源。

所有整体回复必须有明确的 `reply_to`（原提交 message ID），定位回复还需匹配 comment／round。缺失、歧义、跨宿主或跨 artifact 关联一律拒绝，不自动选最新消息，不广播。迟到回复只可归入原 `review_epoch` 历史；不能完成新代次评论、改变其颜色、更新当前修订或触发重新打开。reopen 新建 epoch 后，不复用旧消息身份，也不自动迁移旧草稿为已提交消息。

### 8.2 对外命令

```sh
polish artifact.html
polish poll artifact.html
polish reply artifact.html --review <epoch> --reply-to <message-id> --comment <id> --round <id> --agent-reply "修改说明"
polish reply artifact.html --review <epoch> --reply-to <message-id> --agent-reply "整体回复"
polish end artifact.html
polish artifact.html --reopen
```

上例为目标 CLI 契约，新增关联参数实施时与现有解析器和宿主能力一起落地。未指定 comment 的 reply 是整体回复，不允许把它自动分配给所有评论。所有整体回复均须提供明确的 review／reply-to 关联，不能因只有一个候选就猜测；可信宿主上下文若自动填入，也必须传递并校验确切身份。

`polish` 必须是实际可执行文件；帮助、错误、下一步建议、skill、构建和文档一致。npm 包发布不是首版验收前提，可先本地构建链接；包名可暂用 polish-axi，不能假设 npm 名称已可用。保留上游许可及来源，不为改名批量改写无关内部标识。

运行状态使用独立目录／服务身份，避免和原 lavish 安装相互接管。结束只作用于指定 artifact，服务空闲时沿用安全的自动退出机制。

## 9. 落地位置与开发顺序

| 模块 | 必须完成的改动 |
| --- | --- |
| `src/server.js` 与最小宿主桥接模块 | 主动投递、可靠回执、实时事件、无锚点消息、结束生命周期 |
| `src/session-store.js` / `src/chat-messages.js` | 消息关联、轮次与幂等、待确认／用户完成分离、持久化结束状态 |
| `src/artifact-sdk.js` | 完整文字选区、块定位、浮窗、无数字圆球、避免劫持原生交互 |
| `src/chrome-client.js` / `src/chrome.css` | 替换侧栏、整体会话入口、表单队列入口、实时状态与手动刷新 |
| CLI、skill、构建与设计指导 | polish 入口、当前宿主绑定、固定新 HTML 风格、结束使用契约 |
| README、相关 invariants 与交付回执文档 | 更新各自负责的契约，避免原有自动 Done 文案与新规则冲突 |

1. **M0：P0 通信验证。** 先在当前 Codex 和 Pi 活动会话证明网页可主动投递；记录延迟、忙碌排队和空闲唤醒证据。无法绑定时输出具体限制，不能改为另起会话掩盖。
2. **M1：消息和生命周期。** 实现 anchored/session 两类消息、可靠关联、独立用户完成、关闭／手动结束、断线恢复。通过接口及状态测试。
3. **M2：交互替换。** 在上游真实 SDK 和 chrome 上实现浮窗圆球及整体入口，迁移原侧栏功能，保留原生页面交互。通过浏览器回归。
4. **M3：正式集成验收。** polish 命令与指导统一；Pi 同会话连续两轮修改、回复、验收、结束；提交检查及延迟报告全部通过。

本修订仅供复审，不启动上述任一阶段。M0 须在获准进行受控验证后按 G01–G07 逐宿主提交证据；未通过不得进入 M1–M3，通过也不自动获得完整开发批准。M0 是后续正式开发的前置门槛，不能排到界面完成之后。优先复用现有机制，不重写已有服务器、白板或表单系统。
